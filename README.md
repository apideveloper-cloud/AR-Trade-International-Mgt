# AR Trade International Web Console

One codebase with four faces:

- **Storefront** (`/`): catalogue, cart, checkout with map-priced delivery, customer accounts, blog, chat assistant.
- **Admin console** (`/admin`): orders, catalogue, inventory, quotations, customers, content, marketing, roles, audit, backups.
- **Delivery hub** (`/hub`) and **email marketing** (`/email`): dispatch board, rider app, tracking; campaigns and automations.
- **Field app API** (`/api/field/*`): used by the separate Flutter mobile app (attendance, visits, orders, expenses).

Client: React 18 + Vite. Server: Express 4 + MySQL (`mysql2`), ES modules.

## Requirements

- Node.js (a version with `node --test` and `--watch`; 18+ assumed, unverified) and npm
- A MySQL server reachable with the credentials in `server/.env`

## Install

```
npm run install:all                    # root + server + client dependencies
cp server/.env.example server/.env     # then fill it in (see Environment variables)
npm run db:setup                       # creates missing tables, seeds catalogue/content (keeps orders and users)
```

`npm run db:reset` (inside `server/`) drops every table first and destroys all data.

## Run in development

```
npm run dev
```

Starts both with `concurrently`: the API (`node --watch`, port **4000**, or `PORT`) and the Vite client (port **5173**). Vite proxies `/api` to `http://localhost:4000`. Open `http://localhost:5173`.

## Build and start

```
npm run build    # client -> client/dist
npm run start    # node server/src/index.js (API and built client from one origin)
```

In production the server refuses to start without a `JWT_SECRET` of 24+ characters.

## Tests

```
cd server && npm test     # node --test test/*.test.js
```

There is no client test suite.

## Environment variables (names only; see `server/.env.example`)

| Name | Purpose |
|---|---|
| `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASS`, `DB_NAME` | MySQL connection |
| `PORT` | API port (default 4000) |
| `NODE_ENV` | `production` enables the secret check and same-origin serving |
| `JWT_SECRET` | Signs sign-in tokens (required, long, in production) |
| `SITE_URL` | Public base URL for canonical links, sitemap and emails |
| `SMTP_QUOTE_USER`, `SMTP_QUOTE_PASS` | Mailbox that sends quotations |
| `SMTP_SALES_USER`, `SMTP_SALES_PASS` | Mailbox that sends sales orders and invoices |
| `CONTACT_TO` | Where contact-form mail goes |
| `ANTHROPIC_API_KEY`, `CHAT_MODEL` | Optional: lets the chat assistant use Claude |
| `GEOIP_URL` | Optional: IP-to-place lookup for chat leads (off when empty) |
| `GOOGLE_CLIENT_ID`, `FACEBOOK_APP_ID`, `FACEBOOK_APP_SECRET` | Optional social sign-in |
| `AUDIT_KEEP_DAYS`, `BACKUP_EVERY_HOURS`, `BACKUP_KEEP_DAYS` | Audit and backup retention |
| `FIELD_OFFICE_LAT`, `FIELD_OFFICE_LNG`, `FIELD_ZONE_NAME`, `FIELD_ZONE_KM`, `FIELD_SEED_DEMO`, `PURCHASE_BUDGET` | Field app settings |

Only some of these appear in `.env.example`; the rest were found by searching `process.env` in `server/src`.

## How deployment works

Deployment uses a code-only package: the built client plus server code, with no `node_modules` and no secrets. It is unpacked on the server, dependencies are installed there, and the Node service is restarted. On start, `server/src/migrate.js` adds any new columns and tables, so a restart is required for schema changes to apply. Secrets stay in the server's own `.env`. Step-by-step instructions are in `deploy/DEPLOY.md`. After a deploy, render the key pages in a browser rather than only calling the API.
